# 测试模块文档结构要求（Detailed Legacy Version）

## 1. 总体约束

1. `testing_architecture.md` 保持当前目录结构：
   - 只允许在现有章节下补充内容；
   - 不删除、重命名或调整现有章节顺序；
   - 模块级实现、用例和断言细节应下沉到对应模块文档。

2. 每个测试模块建立独立文档，命名规则为：

```text
testing_${current_function_part}.md
```

3. 每个模块文档统一保留以下九个主章节：

```text
P${part_number} ${module_name} Testing
${part_number}.1 文档定位、模块职责与范围
${part_number}.2 当前已落地范围
${part_number}.3 当前主流程定义
${part_number}.4 用例与断言
${part_number}.5 测试执行链路
${part_number}.6 依赖替换与故障注入
${part_number}.7 当前边界与非目标
${part_number}.8 后续扩展
${part_number}.9 业务 / Mapping 解析
```

4. 本结构是**通用信息约束**，不是要求所有模块完全一致的固定模板：
   - 九个主章节保留；
   - 二级以下标题可根据模块特性调整；
   - 没有实际内容的可选项可以省略；
   - 模块特有内容可以新增，但应放入语义最接近的主章节。

5. 文档中的事实应尽量能追踪到以下证据：
   - 测试文件和测试函数；
   - fixture、mock、stub、fake、spy 或故障注入入口；
   - 被测代码入口；
   - pytest marker、运行命令或 profile；
   - CI workflow、测试报告或质量门禁配置。

6. 建议统一使用以下状态，避免把规划描述成已落地事实：

| 状态 | 含义 |
|---|---|
| `implemented` | 已有可执行测试并满足当前约定 |
| `partial` | 只覆盖部分流程、断言或运行模式 |
| `xfail gap` | 已固定目标契约，但当前实现条件尚不满足 |
| `planned` | 只有设计目标，尚无可执行测试 |
| `out of scope` | 明确不属于当前模块职责 |

# P${part_number} ${module_name} Testing

> 对应 `testing_architecture.md` 中的相关 Part。标题、编号和模块名按实际情况替换。

## ${part_number}.1 文档定位、模块职责与范围

本节回答：**该模块为什么存在、负责保护什么、与整体测试体系是什么关系。**

### 最低要求

1. 说明本文档对应的架构 Part、测试模块或专项能力；
2. 说明模块负责验证的核心功能；
3. 说明主要保护的业务风险或工程风险；
4. 说明模块直接负责的范围；
5. 说明会触达但不完整负责的相邻模块；
6. 说明与其他测试文档的职责边界。

### 推荐结构

```markdown
### ${part_number}.1.1 文档定位
### ${part_number}.1.2 模块职责
### ${part_number}.1.3 测试范围与所有权
### ${part_number}.1.4 核心验证问题
```

### 可选范围表

| 范围类型 | 对象或能力 | 当前模块责任 |
|---|---|---|
| 直接范围 |  |  |
| 相邻边界 |  |  |
| 其他模块负责 |  |  |

“核心验证问题”应以问题形式概括，例如：

1. 主入口或核心能力是否仍然可用？
2. 正常路径是否按约定完成？
3. 异常路径是否能够正确失败、恢复或收尾？
4. 状态、副作用和资源是否保持一致？

问题数量和内容按模块实际调整。

## ${part_number}.4 用例与断言

本节回答：**每条重要测试保护什么风险，通过后能证明什么。**

这是模块文档中应最详细的部分。

### ${part_number}.4.1 用例组织方式

用例可以按以下任一维度分组：

1. 测试文件；
2. 测试层级；
3. 业务能力；
4. 正常路径与异常路径；
5. 运行模式或 profile。

选择最符合当前模块理解方式的一种即可。

### ${part_number}.4.2 单条用例最低信息

每条重要用例至少说明：

```markdown
#### ${part_number}.4.X.X `test_case_name`

- 所属测试文件：
- 当前状态：implemented / partial / xfail gap / planned
- 测试层级或能力组：
- 运行模式：
- Gate 属性：
- 核心目标：
- 保护的主要风险：
- 覆盖流程：
- 关键依赖控制：
- 故障注入（如有）：
- 关键断言：
- 通过后能够证明：
- 当前不能证明：
```

### ${part_number}.4.3 关键断言分类

“关键断言”可按模块实际从以下类型中选择：

1. 输入与前置条件断言；
2. 协议、接口或返回结构断言；
3. 业务结果或事件断言；
4. 流程阶段与生命周期断言；
5. 状态、资源或清理断言；
6. 副作用、调用参数或调用次数断言；
7. 日志、指标或报告字段断言。

不要求每条用例包含所有类型，但不应只写“结果符合预期”。

### ${part_number}.4.4 模块级 Contract / Invariant 汇总

建议在单条用例说明后增加整体覆盖表：

| Contract / Invariant | 当前状态 | 对应用例 | 断言层级 | 缺口说明 |
|---|---|---|---|---|
|  |  |  |  |  |

该表用于展示模块整体覆盖，不替代单条用例说明。

### ${part_number}.4.5 Executable Gap

如存在 `xfail` 或其他可执行缺口，应说明：

1. 期望契约；
2. 当前阻塞原因；
3. 已有的可执行占位；
4. 解除 gap 的完成判据；
5. 在解除前如何标记和报告。

## ${part_number}.5 测试执行链路

本节回答：**测试从执行命令开始，到被测代码、断言和报告结束，中间经过了什么。**

### 最低要求

1. 记录实际执行入口；
2. 说明关键 fixture 和环境准备；
3. 说明被测代码的主要调用链；
4. 说明结果如何被断言；
5. 如存在结构化报告，说明数据如何进入报告或 Gate；
6. 建立测试用例到业务能力和架构 Part 的映射。

### 推荐执行链路

```text
pytest / CI 命令
-> fixture / environment setup
-> dependency replacement
-> 被测入口
-> 核心处理
-> 输出或副作用
-> assertions
-> report / quality gate
```

### 推荐结构

```markdown
### ${part_number}.5.1 执行入口
### ${part_number}.5.2 Fixture 与环境准备
### ${part_number}.5.3 被测代码调用链
### ${part_number}.5.4 测试结果与报告链路
### ${part_number}.5.5 用例到业务 / 架构的映射
```

### 推荐映射表

| 测试用例或能力组 | 被测业务能力 | 关键代码入口 | 相邻模块 | 当前边界 |
|---|---|---|---|---|
|  |  |  |  |  |

只保留与测试目标有关的关键节点，不需要复制完整调用栈。

## ${part_number}.6 依赖替换与故障注入

本节回答：**哪些依赖被控制，为什么控制，控制后仍保留了什么测试价值。**

### 最低要求

1. 列出主要真实依赖和替代依赖；
2. 说明替换方式与替换原因；
3. 说明替换后仍保留的核心路径；
4. 说明当前故障注入场景；
5. 说明 spy、mock、stub 或 fake 的观察目的；
6. 如有结构化观测，说明最小报告字段。

### 推荐依赖矩阵

| 依赖对象 | 处理方式 | 适用模式 | 替换原因 | 保留的真实路径 | 主要观察点 |
|---|---|---|---|---|---|
|  |  |  |  |  |  |

### 推荐故障注入矩阵

| 故障场景 | 注入位置 | 注入方式 | 预期行为 | 关键断言 | 当前状态 |
|---|---|---|---|---|---|
|  |  |  |  |  |  |

### 需要明确的边界

1. 哪些是高波动或外部依赖；
2. 哪些依赖与当前断言目标无关，可以替换；
3. 哪些核心入口、控制流、状态迁移或清理路径不能被替换；
4. 是否存在过度 patch 导致测试失去意义的风险。

### 测试替代对象术语

按当前项目实际使用即可：

- `stub`：提供固定输入或固定返回；
- `fake`：提供可执行但简化的替代实现；
- `mock`：控制并验证依赖交互；
- `spy`：记录调用、参数或次数。

重点是解释其在当前模块中的具体用途，不要求展开成理论说明。

## ${part_number}.7 当前边界与非目标

本节回答：**当前测试结论不能被外推到什么范围。**

### 最低要求

1. 列出当前明确不覆盖的能力；
2. 说明这些能力属于其他模块、其他测试层，还是暂未实现；
3. 说明当前真实性限制；
4. 说明环境、数据和外部依赖限制；
5. 说明为何不继续向相邻模块内部扩张。

### 推荐结构

```markdown
### ${part_number}.7.1 当前明确不覆盖
### ${part_number}.7.2 当前结论的真实性限制
### ${part_number}.7.3 环境与数据限制
### ${part_number}.7.4 与其他模块的非重复边界
```

边界原因可区分为：

1. 属于其他架构 Part；
2. 属于其他测试层；
3. 不适合作为当前 Gate；
4. 主代码尚无稳定契约；
5. 当前优先级较低；
6. 已由其他测试资产承担。

## ${part_number}.8 后续扩展

本节回答：**下一步补什么，以及补到什么程度才算完成。**

### 最低要求

1. 按风险和工程价值排序；
2. 说明每项扩展的当前缺口；
3. 说明扩展前置条件；
4. 说明建议测试层级或运行模式；
5. 说明是否进入 blocking、non-blocking、nightly 或 manual；
6. 给出可验证的完成判据。

### 推荐扩展项模板

```markdown
### ${part_number}.8.X ${extension_name}

- 当前缺口：
- 扩展目标：
- 前置条件：
- 建议测试层级：
- 建议运行模式：
- 建议 Gate 定位：
- 完成判据：
```

推荐优先顺序：

1. 修复高风险 contract gap；
2. 补齐关键异常和清理语义；
3. 提高核心路径真实性；
4. 增加必要的跨模块覆盖；
5. 扩展到更真实环境或更高层级 Gate。

不要求所有规划项一次完成，也不应把远期目标写成当前承诺。

| 测试资产 | 主要架构 Part | 触达的相邻 Part | 映射原因 | 当前责任边界 |
|---|---|---|---|---|
|  |  |  |  |  |

### 跨模块归属判断原则

当一条测试触达多个模块时，优先根据以下因素判断归属：

1. 测试从哪个入口观察行为；
2. 主要断言落在哪个模块的外显契约；
3. 哪个模块承担失败后的直接责任；
4. 哪些内部能力仍需要在对应模块中单独测试。

## 10. 模块文档完成检查

### 10.1 事实与证据

- [ ] “已落地”内容能定位到真实测试文件或配置；
- [ ] 测试函数、代码入口、命令和 marker 名称准确；
- [ ] 没有把 `planned` 内容描述为已实现；
- [ ] 没有把局部真实路径描述为完整端到端真实路径。

### 10.2 用例与断言

- [ ] 重要用例说明了目标、风险和关键断言；
- [ ] 断言不只停留在“未报错”或单一状态码；
- [ ] 按需要区分了业务结果、流程、状态清理和副作用；
- [ ] 说明了测试通过后能证明和不能证明什么。

### 10.3 依赖与边界

- [ ] 说明了主要 stub、mock、fake、spy 和真实依赖；
- [ ] 说明了替换原因和保留的核心路径；
- [ ] 明确当前非目标及其他模块责任；
- [ ] 跨 Part 测试说明了归属依据。

### 10.4 执行与维护

- [ ] 记录了当前实际执行入口和 Gate 属性；
- [ ] 自动化执行范围与文档结论一致；
- [ ] 九个主章节的职责没有明显重复；
- [ ] 模块特有内容放入对应章节，而不是修改总架构结构；
- [ ] 文档足以支持代码审查和测试扩展，但没有复制完整源码。
